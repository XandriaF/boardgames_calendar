# Миграция с Netlify + Apps Script на свой сервер и домен

Это план, не код — код пишем отдельным шагом, после того как согласуем архитектуру
(так решили). Ниже — что меняется, что остаётся, и по шагам, что делать.

## Итоговая архитектура

```
Пользователь → https://ваш-домен.ru → nginx на вашем сервере
                                         ├─ отдаёт статику сайта (index.html, app.js, ...)
                                         └─ проксирует /api/* → Node-бэкенд (localhost:3001)
                                                                    │
                                                                    ├─ SQLite (файл на диске) -- основной источник данных
                                                                    │
                                                                    └─ раз в N минут, в фоне, СНАЧАЛА pull, ПОТОМ push:
                                                                       ├─ pull: «Заявки», роль амбассадора, + ручные правки в «Мероприятия»/«Записи» → в SQLite
                                                                       └─ push: актуальный срез событий/записей/голосов из SQLite → в таблицу (для наглядности, бэкапа и чтобы ваши правки не потерялись)
```

Главное смещение: сейчас Google Sheets — это одновременно и хранилище, и бэкенд (каждый
клик на сайте — это чтение/запись в таблицу через Apps Script). После миграции бэкенд —
ваш сервер и SQLite, а таблица становится **зеркалом для людей, с возможностью править
руками**: каталог игр «Заявки» и роль «Амбассадор» как правились в таблице, так и
продолжите; «Мероприятия» и «Записи» — тоже можно поправить прямо в таблице (опечатка в
игре, дата, вручную скорректировать, кто записан) — сервер подхватит правку в
ближайшем цикле синхронизации (см. шаг 6). Это не отменяет того, что сервер — основной,
всегда актуальный источник для самого сайта; таблица просто перестаёт быть местом, где
происходит каждый клик пользователя, но остаётся полноценно редактируемой вручную.

**Почему Node.js**, даже раз пока не известно, на чём бот: в `tests/mock-server.js` уже
лежит рабочая, протестированная реализация ровно этой бизнес-логики (лимиты мест, PIN-
аккаунты, закрытые мероприятия, публикация черновиков, голоса) — на чистом Node,
через `http.createServer`, только вместо базы — массивы в памяти. Реальный бэкенд — это,
по сути, тот же файл, но с SQLite вместо массивов и с добавленной синхронизацией с
таблицей. Экономит по-настоящему много времени на шаге «переписать код Code.gs». Если
окажется, что бот всё-таки на Python — архитектура ниже не меняется, меняется только
код (FastAPI + APScheduler + google-api-python-client вместо Express + node-cron +
googleapis) — скажете, и я пересоберу план под это.

**Что не меняется вообще:** сама Google-таблица (тот же URL/ID, те же вкладки), лист
«Заявки» и колонка «Роль» в «Аккаунты» правятся руками ровно как сейчас, лист
«Календарь» продолжает существовать в прежнем виде. Фронтенд (HTML/CSS/JS) почти не
меняется — все страницы уже ходят на бэкенд через одинаковый `apiGet(action, params)` /
`apiPost({action, ...})`, так что после переезда меняется буквально одна строчка —
`APPS_SCRIPT_URL` в `config.js`.

## Шаг 2. Подготовка сервера

```bash
sudo apt update && sudo apt upgrade -y

# build-essential -- на случай, если better-sqlite3 на этой связке ОС/Node не найдёт
# готовый прекомпилированный бинарник и попытается собрать нативный модуль сама (см.
# ниже про запасной вариант с node:sqlite -- он ставится и без этого, но лучше иметь)
sudo apt install -y build-essential python3

# Node.js -- через nvm, а не NodeSource: Ubuntu 26.04 очень свежая (на момент написания
# плана), под неё у NodeSource может ещё не быть готового .deb-репозитория. nvm ставит
# Node из официальных бинарников node.js напрямую, от версии ОС не зависит.
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
source ~/.bashrc
nvm install --lts
node -v; npm -v

# nginx
sudo apt install -y nginx

# swap-файл -- на сервере 2 ГБ RAM и сейчас 0 подкачки (см. разведку, шаг 0). 2 ГБ swap --
# страховка от OOM (например, если что-то соберётся из исходников или подскочит трафик),
# для SQLite+Node за глаза
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h   # проверить, что подкачка появилась

# файрвол -- открываем только то, что нужно (порт 10050/zabbix уже слушает -- не трогаем,
# порты 3001 и 80/443 ничем не заняты, см. разведку)
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'   # 80 + 443
sudo ufw enable
sudo ufw status
```

Docker на сервере уже стоит, но специально его не используем — Node ставится напрямую и
без него, а через `nvm` быстрее и проще обновлять версию в будущем. Если впоследствии
захочется деплоить контейнером — архитектура (nginx → localhost:3001) от этого не
меняется, тогда просто оборачиваем `src/app.js` в `Dockerfile` и меняем `ExecStart` в
systemd-юните (или вообще заменяем юнит на `docker run`).

Директория для сайта и бэкенда — например:
```bash
sudo mkdir -p /var/www/nastolki/site      # сюда — статика (index.html, app.js, ...)
sudo mkdir -p /var/www/nastolki/server    # сюда — Node-бэкенд + SQLite-файл
sudo chown -R $USER:$USER /var/www/nastolki
```

## Шаг 3. nginx + бесплатный SSL (Let's Encrypt)

`/etc/nginx/sites-available/nastolki` (уже есть готовый в новом репозитории —
`deploy/nginx.conf.example`, просто заменить домен и скопировать):
```nginx
server {
    listen 80;
    server_name nastolki.ваш-домен.ru;

    root /var/www/nastolki/site;
    index index.html;

    # location /api БЕЗ конечного слэша + proxy_pass БЕЗ пути после адреса -- нарочно.
    # Фронтенд обращается на .../api?action=events (без слэша перед "?"). Если написать
    # "location /api/ { proxy_pass http://127.0.0.1:3001/; }" (оба со слэшем) — такой
    # запрос вообще не совпадёт с этим location'ом и улетит в 404 ещё на уровне nginx, не
    # долетев до бэкенда. Вариант ниже передаёт бэкенду запрос ровно с тем же URI, каким
    # он пришёл.
    location /api {
        proxy_pass http://127.0.0.1:3001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /health {
        proxy_pass http://127.0.0.1:3001;
    }
}
```
```bash
sudo ln -s /etc/nginx/sites-available/nastolki /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# бесплатный сертификат, сам допишет https-блок и настроит автопродление
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d nastolki.ваш-домен.ru
```
Проверка автопродления: `sudo certbot renew --dry-run`.

Поскольку сайт и `/api` теперь на одном домене — можно будет вообще убрать CORS-обходы
(`text/plain` вместо `application/json` в заголовках POST), которые сейчас нужны только
из-за того, что Apps Script живёт на отдельном домене `script.google.com`. Не обязательно
делать это сразу, но это одно из мелких упрощений, которые появятся сами.

## Шаг 4. Бэкенд: структура — ✅ код написан и лежит в `server_boardgames_calendar`

Порт `3001`, только на `127.0.0.1` — наружу торчит только nginx.

Фактическая структура (в репозитории `server_boardgames_calendar`):
```
src/
  app.js              -- Express, монтирует роутер + /health
  db.js               -- SQLite: better-sqlite3, с автофолбэком на встроенный node:sqlite
  lib/helpers.js       -- capitalizeFirst/normalizeEmail/eventKey/... -- те же, что в Code.gs
  logic/

    requests.js          -- каталог «Заявки», handleVote/Unvote
  routes/api.js        -- GET/POST /api, тот же контракт action-ов, что и сейчас
  sync/
    sheetsClient.js     -- авторизация сервисным аккаунтом, чтение/запись диапазонов
    pull.js              -- таблица → SQLite (сначала, см. шаг 6)
    push.js               -- SQLite → таблица (потом)
    scheduler.js          -- node-cron, раз в N минут: pull затем push

.env                   -- ключ сервисного аккаунта, ID таблицы, порт (не в git, есть .env.example)
tests/run-api-test.js  -- 61 проверка через настоящий HTTP-запрос к настоящему Express+SQLite

  nastolki.service.example -- см. ниже
```
Таблицы SQLite — по одной на каждый нынешний лист: `events`, `signups`, `votes`,
`requests_catalog`, `accounts`, `ambassador_roles` (роль — отдельно от `accounts`, чтобы
синк не затирал вручную проставленную в таблице роль человеку, который ещё ни разу не
идентифицировался на сайте). Роуты `/api` — тот же контракт action-ов, что и сейчас
(`events`, `requests`, `identify`, `signup`, `cancel`, `interest`, `publish`,
`createEvent`, `adjustReserved`, `vote`, `unvote`) — фронтенду не нужно ничего менять,
кроме `APPS_SCRIPT_URL` в `config.js` (шаг 8).

**Что уже протестировано:** вся бизнес-логика выше (лимиты мест, закрытые мероприятия,
видимость черновиков/запланированных, PIN-аккаунты, голоса) — через `tests/run-api-test.js`,
настоящий HTTP-запрос к настоящему поднятому Express-приложению. Этот тест по ходу
поймал реальный баг (SQLite не умеет `lower()` для кириллицы — голоса за игры сравнивались
некорректно) — уже исправлено.

**Что пока не проверено вживую:** весь `sync/` — написан по спецификации (шаг 6), но
ни разу не выполнялся против настоящей Google-таблицы (у меня нет прямого доступа в
интернет из песочницы, где пишется код). Нужно будет прогнать и проверить на реальных
данных на первом же цикле после того, как появится сервисный аккаунт (шаг 5) — особенно
`pull.js`, где даты/время конвертируются из числового serial-формата Google Sheets.

Автозапуск/рестарт при падении — через systemd-юнит (`deploy/nastolki.service.example`,
просто скопировать):
```ini
# /etc/systemd/system/nastolki.service
[Unit]
Description=Настолки — бэкенд
After=network.target

[Service]
WorkingDirectory=/var/www/nastolki/server
ExecStart=/usr/bin/node src/app.js
Restart=always
RestartSec=3
User=www-data
EnvironmentFile=/var/www/nastolki/server/.env

[Install]
WantedBy=multi-user.target
```
(Путь к `node` в `ExecStart` — если ставили через `nvm`, узнать точный через `which node`
и подставить сюда абсолютный путь: systemd не видит `nvm`-шелл-функцию, нужен полный путь
до бинарника.)

## Шаг 5. Сервисный аккаунт Google (для связи с таблицей)

Это разовая настройка в Google Cloud Console (на том же Google-аккаунте, где лежит
таблица):

1. console.cloud.google.com → создать проект (или использовать существующий).
2. «APIs & Services» → «Library» → включить **Google Sheets API**.
3. «APIs & Services» → «Credentials» → «Create Credentials» → **Service Account**.
4. У созданного аккаунта — «Keys» → «Add key» → **JSON**, скачается файл-ключ.
5. Откройте саму Google-таблицу → «Настройки доступа» → добавьте email сервисного
   аккаунта (вида `что-то@проект.iam.gserviceaccount.com`) с правом **Редактор**.
6. Файл-ключ загрузите на сервер в `/var/www/nastolki/server/.env` (или отдельным
   json-файлом рядом), `chmod 600`, в `.gitignore`.

Дальше сервер обращается к таблице от имени этого аккаунта через `googleapis` — без
Apps Script и без веб-приложения вообще, таблица используется просто как обычная
Google-таблица через API.

## Шаг 6. Синхронизация с таблицей

Уточнение по ходу: кроме каталога «Заявки» и роли амбассадора, вы хотите ещё **править
записи и корректировать анонс прямо в таблице** («Мероприятия» и «Записи») — например,
поправить опечатку в игре, дату, или вручную скорректировать, кто записан. Это делает
эти два листа не чисто зеркалом, а полноценно двусторонними. Ниже — как это сделать
надёжно.

**Нужен ID-столбец.** Сейчас строки в «Мероприятия»/«Записи» различаются только по
содержимому (дата+время+игра, дата+время+игра+email) — если поправить руками сами эти
поля, сервер не поймёт, что это «та же строка, но исправленная», а не новая. Поэтому
дописываем в **конец** каждого из этих двух листов новый столбец **«ID»** (просто
следующий свободный справа — не вставляем в начало, ничего не сдвигается, нынешний
`Code.gs` эти столбцы не читает и продолжит работать как есть). Сервер сам проставляет
туда числа при первом переносе и при появлении новых строк — руками туда лезть не
нужно, разве что оставить пустым для новой строки, вписанной вручную (сервер подхватит
её как новую и присвоит ID сам).

**Каждый цикл синхронизации (например, раз в 5-10 минут) — сначала pull, потом push:**

1. **Pull** «Мероприятия»/«Записи»: построчно сверяем с тем, что сервер сам туда в
   прошлый раз записал (хранится рядом, в SQLite). Совпало — пропускаем. Есть ID и
   строка отличается — значит, кто-то поправил её руками в таблице → обновляем эту
   запись на сервере. Строка без ID — значит, добавлена руками → создаём на сервере,
   присваиваем ID. Строки, пропавшие из таблицы, **не удаляем** на сервере (мало ли,
   случайно стёрли) — это делает только сам сайт (отмена записи и т.п.).
2. Заодно pull «Заявки» целиком и столбца «Роль» в «Аккаунты» — как и раньше.
3. **Push**: перезаписывает «Мероприятия», «Записи», «Заявки_голоса», Email/Имя/PIN/Дату
   в «Аккаунты» (столбец «Роль» не трогаем) актуальным срезом с сервера — включая то,
   что только что подтянули из pull, плюс всё, что случилось на сайте с прошлого цикла.
   Заодно пересобирает лист «Календарь».

Порядок «сначала pull» — специально: то, что вы поправили руками, попадает на сервер
ДО того, как push успеет затереть это старой версией.

**Если один и тот же анонс за 5-10 минут поправят и в таблице, и кто-то одновременно
запишется/отменится на сайте** — эта версия победит: последняя по времени на момент
pull. Для внутреннего инструмента с таким трафиком это редкий и не критичный случай, но
раз вы теперь регулярно правите руками — стоит знать. Если захотите подстраховаться
сильнее (например, блокировать одновременное редактирование) — это отдельная, более
сложная задача, для старта не нужна.

Голоса («Заявки_голоса») остаются **только** push (сервер → таблица) — этот лист
событийный (по записи на каждый клик), руками его никто не правит.

## Шаг 7. Перенос существующих данных — отдельный скрипт не нужен

Изначально планировался разовый скрипт-мигратор. Оказалось, он не нужен: `sync/pull.js`
и так по ID-у решает «это уже известная серверу строка или новая» (шаг 6) — если
прогнать `pullAll` на **пустой** базе, у вообще всех строк в «Мероприятия»/«Записи» нет
ID, поэтому pull создаёт их все как новые, то есть выполняет ровно полный перенос
истории. То же для «Заявки» и роли амбассадора — та же логика, что и в обычном цикле
синхронизации.

На практике это означает: перенос данных = самый первый запуск бэкенда с пустым
`data/nastolki.db` и настроенным `.env` (шаг 5). Ничего отдельно готовить/запускать не
нужно. Сверить результат можно вручную — сравнить количество строк в «Мероприятия» с
`SELECT count(*) FROM events` и т.п. до переключения сайта (шаг 9).

## Шаг 9. Переключение (cutover)

1. Полностью протестировать новый бэкенд ДО переключения DNS/конфига — например, зайдя
   на сайт по IP сервера или временно прописав домен в `/etc/hosts` на своём компьютере.
2. Выбрать спокойное время (мало кто пользуется сайтом).
3. Прогнать миграцию (шаг 7) в последний раз, для самого свежего среза.
4. Обновить `config.js` (шаг 8.2), задеплоить.
5. Проверить вручную: идентификация (имя+почта+код), запись на игру/отмена, голос за
   игру в «Приём заявок», анонс новой игры, «Мои игры».
6. Apps Script/Netlify пока не трогать — держите их живыми ещё недели 1-2 как
   подстраховку (если что-то всплывёт — откатиться это просто вернуть старое значение
   `APPS_SCRIPT_URL` и передеплоить на Netlify). Потом можно спокойно снести Netlify-сайт
   и, если не жалко, деплой Apps Script (саму таблицу — не трогать, она остаётся).

## Шаг 10. Бэкапы

SQLite — это один файл, бэкапить тривиально:
```bash
# cron, раз в сутки
sqlite3 /var/www/nastolki/server/data/nastolki.db ".backup /var/www/nastolki/backups/nastolki-$(date +\%F).db"
```
Плюс сама Google-таблица (раз она обновляется push-синком) — это по сути ещё один,
человекочитаемый бэкап бесплатно. Не лишним будет докидывать дневные бэкапы туда же,
куда сейчас бэкапится бот (раз инфраструктура для этого уже есть).
