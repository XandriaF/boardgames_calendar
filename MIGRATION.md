# Миграция с Netlify + Apps Script на свой сервер и домен

Это план, не код — код пишем отдельным шагом, после того как согласуем архитектуру
(так решили). Ниже — что меняется, что остаётся, и по шагам, что делать.

## Итоговая архитектура

```
Пользователь → https://ваш-домен.ru → nginx на вашем сервере
                                         ├─ отдаёт статику сайта (index.html, app.js, ...)
                                         └─ проксирует /api/* → Node-бэкенд (localhost:3001)
                                                                    │
                                                                    ├─ SQLite (файл на диске) -- основной источник данных
                                                                    │
                                                                    └─ раз в N минут, в фоне:
                                                                       ├─ push: события/записи/голоса → в гугл-таблицу (для наглядности и бэкапа)
                                                                       └─ pull: каталог «Заявки» и роль амбассадора из таблицы → в SQLite (эти 2 вещи по-прежнему правите руками в таблице)
```

Главное смещение: сейчас Google Sheets — это одновременно и хранилище, и бэкенд (каждый
клик на сайте — это чтение/запись в таблицу через Apps Script). После миграции бэкенд —
ваш сервер и SQLite, а таблица становится **зеркалом для людей**: то, что обычно смотрят
и правят руками (каталог игр «Заявки», роль «Амбассадор» в «Аккаунты»), остаётся
редактируемым в таблице как сейчас; всё остальное (события, записи, голоса) сервер сам
периодически выгружает в таблицу — просто чтобы она не расходилась с реальностью и
служила бэкапом.

**Почему Node.js**, даже раз пока не известно, на чём бот: в `tests/mock-server.js` уже
лежит рабочая, протестированная реализация ровно этой бизнес-логики (лимиты мест, PIN-
аккаунты, закрытые мероприятия, публикация черновиков, голоса) — на чистом Node,
через `http.createServer`, только вместо базы — массивы в памяти. Реальный бэкенд — это,
по сути, тот же файл, но с SQLite вместо массивов и с добавленной синхронизацией с
таблицей. Экономит по-настоящему много времени на шаге «переписать код Code.gs». Если
окажется, что бот всё-таки на Python — архитектура ниже не меняется, меняется только
код (FastAPI + APScheduler + google-api-python-client вместо Express + node-cron +
googleapis) — скажете, и я пересоберу план под это.

**Что не меняется вообще:** сама Google-таблица (тот же URL/ID, те же вкладки), лист
«Заявки» и колонка «Роль» в «Аккаунты» правятся руками ровно как сейчас, лист
«Календарь» продолжает существовать в прежнем виде. Фронтенд (HTML/CSS/JS) почти не
меняется — все страницы уже ходят на бэкенд через одинаковый `apiGet(action, params)` /
`apiPost({action, ...})`, так что после переезда меняется буквально одна строчка —
`APPS_SCRIPT_URL` в `config.js`.

## Шаг 0. Разведка сервера

Раз стек бота пока не известен — первым делом смотрим, что там уже есть. Подключитесь по
SSH и выполните:

```bash
cat /etc/os-release          # какая ОС и версия (Ubuntu/Debian/др.)
node -v; npm -v              # есть ли уже Node.js
python3 --version            # или Python
docker --version             # или всё живёт в докере
pm2 list                     # process-manager для бота?
systemctl list-units --type=service --state=running | grep -i bot
nginx -v 2>&1; which caddy   # уже стоит веб-сервер?
crontab -l                   # что-то уже запланировано?
df -h; free -h               # место на диске / память (для SQLite и Node за глаза хватит и 512 МБ-1 ГБ)
ss -tulpn | grep LISTEN      # какие порты уже заняты (чтобы не столкнуться с ботом)
```

Пришлите мне вывод (или перескажите своими словами) — тогда шаги 2-4 ниже я уточню под
конкретно ваш сервер. Дальше в инструкции исхожу из типового варианта: Ubuntu/Debian,
доступ по SSH с sudo, ничего специфичного ещё не стоит.

## Шаг 1. Домен

1. Если домена ещё нет — купите у любого регистратора (reg.ru, timeweb, Namecheap и
   т.п.), без разницы для дальнейшей настройки.
2. В панели регистратора (или там, где сейчас настроен DNS) добавьте A-запись,
   указывающую на **публичный IP вашего сервера**:
   ```
   Тип   Имя              Значение
   A     nastolki         <IP сервера>      (или @ / без поддомена — как вам удобнее)
   ```
3. Подождите, пока DNS обновится (обычно от нескольких минут до пары часов), проверяйте:
   ```bash
   dig +short nastolki.ваш-домен.ru
   ```
   Как только видите правильный IP — можно переходить к SSL (шаг 3).

## Шаг 2. Подготовка сервера

```bash
sudo apt update && sudo apt upgrade -y

# Node.js LTS (если ещё не стоит — см. разведку в шаге 0)
curl -fsSL https://deb.nodesource.com/setup_lts.x | sudo -E bash -
sudo apt install -y nodejs

# nginx, если ещё не стоит
sudo apt install -y nginx

# файрвол -- открываем только то, что нужно
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'   # 80 + 443
sudo ufw enable
sudo ufw status
```

Директория для сайта и бэкенда — например:
```bash
sudo mkdir -p /var/www/nastolki/site      # сюда — статика (index.html, app.js, ...)
sudo mkdir -p /var/www/nastolki/server    # сюда — Node-бэкенд + SQLite-файл
sudo chown -R $USER:$USER /var/www/nastolki
```

## Шаг 3. nginx + бесплатный SSL (Let's Encrypt)

`/etc/nginx/sites-available/nastolki`:
```nginx
server {
    listen 80;
    server_name nastolki.ваш-домен.ru;

    root /var/www/nastolki/site;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:3001/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```
```bash
sudo ln -s /etc/nginx/sites-available/nastolki /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# бесплатный сертификат, сам допишет https-блок и настроит автопродление
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d nastolki.ваш-домен.ru
```
Проверка автопродления: `sudo certbot renew --dry-run`.

Поскольку сайт и `/api` теперь на одном домене — можно будет вообще убрать CORS-обходы
(`text/plain` вместо `application/json` в заголовках POST), которые сейчас нужны только
из-за того, что Apps Script живёт на отдельном домене `script.google.com`. Не обязательно
делать это сразу, но это одно из мелких упрощений, которые появятся сами.

## Шаг 4. Бэкенд: структура (когда дойдём до кода)

Порт `3001` (или любой свободный, не пересекающийся с ботом), только на `127.0.0.1` —
наружу торчит только nginx.

Предлагаемая структура:
```
/var/www/nastolki/server/
  app.js              -- Express, роуты /api?action=... (GET) и POST /api {action, ...}
  db.js               -- SQLite (better-sqlite3), схема + миграции
  sync/
    pushToSheets.js    -- события/записи/голоса/аккаунты → таблица (раз в N минут)
    pullFromSheets.js  -- «Заявки» и «Аккаунты»!Роль → SQLite (раз в N минут)
  data/nastolki.db     -- сам файл SQLite
  .env                 -- ключ сервисного аккаунта, ID таблицы, порт (не в git)
  package.json
```
Таблицы SQLite — по одной на каждый нынешний лист: `events`, `signups`, `votes`,
`requests_catalog`, `accounts`, с теми же полями, что сейчас пишет `Code.gs`. Роуты
`/api` держим с тем же контрактом action-ов, что и сейчас (`events`, `requests`,
`identify`, `signup`, `cancel`, `interest`, `publish`, `createEvent`, `adjustReserved`,
`vote`, `unvote`) — именно поэтому фронтенду почти ничего не нужно менять.

Автозапуск/рестарт при падении — через `pm2` (если он уже используется для бота) либо
через systemd-юнит:
```ini
# /etc/systemd/system/nastolki.service
[Unit]
Description=Настолки — бэкенд
After=network.target

[Service]
WorkingDirectory=/var/www/nastolki/server
ExecStart=/usr/bin/node app.js
Restart=always
User=www-data
EnvironmentFile=/var/www/nastolki/server/.env

[Install]
WantedBy=multi-user.target
```

## Шаг 5. Сервисный аккаунт Google (для связи с таблицей)

Это разовая настройка в Google Cloud Console (на том же Google-аккаунте, где лежит
таблица):

1. console.cloud.google.com → создать проект (или использовать существующий).
2. «APIs & Services» → «Library» → включить **Google Sheets API**.
3. «APIs & Services» → «Credentials» → «Create Credentials» → **Service Account**.
4. У созданного аккаунта — «Keys» → «Add key» → **JSON**, скачается файл-ключ.
5. Откройте саму Google-таблицу → «Настройки доступа» → добавьте email сервисного
   аккаунта (вида `что-то@проект.iam.gserviceaccount.com`) с правом **Редактор**.
6. Файл-ключ загрузите на сервер в `/var/www/nastolki/server/.env` (или отдельным
   json-файлом рядом), `chmod 600`, в `.gitignore`.

Дальше сервер обращается к таблице от имени этого аккаунта через `googleapis` — без
Apps Script и без веб-приложения вообще, таблица используется просто как обычная
Google-таблица через API.

## Шаг 6. Синхронизация с таблицей

**Push (сервер → таблица), например раз в 10-15 минут:**
- Перезаписывает диапазоны «Мероприятия», «Записи», «Заявки_голоса», и в «Аккаунты» —
  только столбцы Email/Имя/PIN/Дата регистрации (столбец «Роль» — не трогаем, это
  единственное, что вписывается только руками).
- Пересобирает лист «Календарь» — той же логикой, что сейчас в `rebuildCalendar()`.
- Один `batchUpdate`-вызов на весь срез — быстро и без риска упереться в лимиты API.

**Pull (таблица → сервер), тем же интервалом:**
- Читает лист «Заявки» целиком (это ваш каталог игр — как правили руками, так и
  продолжите) → обновляет `requests_catalog` в SQLite.
- Читает столбец «Роль» из «Аккаунты» → обновляет роли в SQLite (единственное, что
  когда-либо приходит ИЗ таблицы В сервер).

Так каталог игр и назначение амбассадоров остаются ровно там же, где вы к ним уже
привыкли, а всё «горячее» (клики на сайте) не ждёт медленный round-trip до Google API
на каждый чих.

## Шаг 7. Перенос существующих данных

Разовый скрипт (тем же сервисным аккаунтом, читает всё через Sheets API):
1. Читает «Мероприятия», «Записи», «Заявки», «Заявки_голоса», «Аккаунты» целиком.
2. Построчно вставляет в соответствующие таблицы SQLite (та же логика парсинга
   дат/времени/чекбоксов, что сейчас в `Code.gs`).
3. В конце — сверка: количество строк в каждой таблице SQLite == количество
   заполненных строк в соответствующем листе. Если разошлось — не переключаем сайт,
   разбираемся.

Гонять его можно сколько угодно раз до переключения (он просто перезатирает SQLite
свежим срезом) — ничего не удаляет и не портит в самой таблице.

## Шаг 8. Обновить сайт

1. Скопировать статические файлы (`index.html`, `app.js`, `organizer.html`,
   `organizer.js`, `requests.html`, `requests.js`, `info.html`, `info.js`, `my.html`,
   `my.js`, `styles.css`, `config.js`) в `/var/www/nastolki/site/` — либо разово
   `scp`/`rsync`, либо `git clone`/`git pull` прямо на сервере (второе удобнее для
   будущих обновлений — тогда деплой это просто `git pull` в этой папке).
2. В `config.js` — единственная содержательная правка:
   ```js
   window.APP_CONFIG = { APPS_SCRIPT_URL: 'https://nastolki.ваш-домен.ru/api' };
   ```

## Шаг 9. Переключение (cutover)

1. Полностью протестировать новый бэкенд ДО переключения DNS/конфига — например, зайдя
   на сайт по IP сервера или временно прописав домен в `/etc/hosts` на своём компьютере.
2. Выбрать спокойное время (мало кто пользуется сайтом).
3. Прогнать миграцию (шаг 7) в последний раз, для самого свежего среза.
4. Обновить `config.js` (шаг 8.2), задеплоить.
5. Проверить вручную: идентификация (имя+почта+код), запись на игру/отмена, голос за
   игру в «Приём заявок», анонс новой игры, «Мои игры».
6. Apps Script/Netlify пока не трогать — держите их живыми ещё недели 1-2 как
   подстраховку (если что-то всплывёт — откатиться это просто вернуть старое значение
   `APPS_SCRIPT_URL` и передеплоить на Netlify). Потом можно спокойно снести Netlify-сайт
   и, если не жалко, деплой Apps Script (саму таблицу — не трогать, она остаётся).

## Шаг 10. Бэкапы

SQLite — это один файл, бэкапить тривиально:
```bash
# cron, раз в сутки
sqlite3 /var/www/nastolki/server/data/nastolki.db ".backup /var/www/nastolki/backups/nastolki-$(date +\%F).db"
```
Плюс сама Google-таблица (раз она обновляется push-синком) — это по сути ещё один,
человекочитаемый бэкап бесплатно. Не лишним будет докидывать дневные бэкапы туда же,
куда сейчас бэкапится бот (раз инфраструктура для этого уже есть).

  хотите резче — выключить сразу?
